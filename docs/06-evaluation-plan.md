# Evaluation plan

Every metric ties back to a design decision it validates or challenges.

| ID | Question | Decision it tests | Variable (x) | Measured (y) | Repetitions | Tool |
|---|---|---|---|---|---|---|
| E1 | Does the model detect fires well? | ML vs rule baseline | model / threshold | precision, recall, detection delay | | |
| E2 | Is the alarm fast enough? | edge decision | load (messages/s) | latency (mean, p95) | ≥ 3 | |
| E3 | How much data does the edge save? | edge/cloud split | mode (edge vs cloud-only) | bytes and messages to cloud | ≥ 3 | |
| E4 | How does the system behave under a burst? | broker/edge capacity | simultaneous nodes | alarms delivered, latency | ≥ 3 | |
| E5 | Does the edge fit a small device? | resource limits | load, CPU limit | CPU %, memory, latency | ≥ 3 | `docker stats` |
| E6 | What is the protocol overhead? | message format and protocol | payload format | bytes on the wire per message | | Wireshark / MQTT Explorer |

## Protocol (each experiment)
1. Fixed configuration (commit hash, `.env`, machines, network).
2. Warm-up, steady state, duration.
3. Raw output saved under `experiments/<id>/`.
4. Plot generated by a script, not by hand.
5. Limitations stated.

Relate results to theory (e.g. expected vs measured latency, bandwidth, message overhead).
